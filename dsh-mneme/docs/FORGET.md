# 选择性遗忘与事实更正（#532）

> 这篇回答 #532 的三个确认请求：现象的根因链、当前机制能承诺什么、以及修复方向需要维护者拍板的取舍。全部结论出自 `main`（514d238）源码逐行核实与一个**零 LLM 的合成轨迹**——不需要真实用户库，任何人按 §4 的步骤能在空库上重现同一结构性结果。

## 1. 现象与根因链

#532 的观察：更正两个事实（颜色 + 整理时间）→ 只要求忘掉颜色 → 新对话里颜色确实不知道，**但整理时间答回了更正前的旧值**。

根因是三段机制的接缝，每一段单独看都符合自己的契约：

1. **更正落成新行，旧行保持活跃。** `autoSummarize` 写入走 `saveWithDedupe` 的 `(type, title, scope)` 三元组去重——更正行的标题与原行不同（蒸馏器按内容起标题），去重不命中，于是**同一事实的两个版本同时活跃**。会清理这种并存的是 dream 的冲突裁决（loser 归档）——但它是阈值门控的（`dreamThresholdCount` 默认 100，#532 现场 13 条、`dream_runs` 0 行，裁决从未运行）。`summarizeDedupeMode`（#127，默认 off）帮不上：它只在**同会话**的时间窗内并（`findSessionDuplicate` 按 `type+source+时间窗` 找候选），而 #532 的更正发生在另一个会话。
2. **`memory_forget` 是行粒度的。** 它按 ID 翻 `forgotten` 标志（抑制注入/检索/列表，原文留存可恢复）——这是接口契约，**不是**「忘掉某个事实」：事实散在几行里，它就只管被点名的那一行。#532 的更正把两个新值合流在一行（蒸馏器把「颜色改成浅橙色 + 时间改成周六 09:00」写进同一条），忘掉「颜色」的操作抑制了这一行，**新的整理时间跟它一起退出可见面**。
3. **旧值行成了唯一幸存的载体。** 旧值（雾蓝色 + 周三 20:00）至少还活在另一行里（6 次蒸馏 × 每次 ≤3 条 = 13 行的库完全装得下独立的旧时间行）。新值行被抑制后，检索/注入面只剩旧值行——模型如实回答了它唯一能看到的东西。旧值行里同样有旧颜色，模型答「不知道颜色」是因为该行也已被抑制（或未入召回窗）——两半行为各自都有解释，合起来才是「保留的更正事实答回旧值」。

**一句话定性：这不是某一行写错了，而是「更正的失效关系」在 dream 第一次运行之前根本不存在。** 旧行与新行之间没有任何持久链接，任何一方的隐藏都不会波及另一方；趁虚而入的是结构，不是某个 bug 的触发。

## 2. 三个确认请求的源码级回答

**Q1：更正两个事实、只忘一个时，推荐怎样保住另一个？**

当前机制下的推荐做法（不需要新配置）：

- **更正时点名旧行**：用 `memory_update` 直接改原行的内容（同标题走 `saveWithDedupe` 的更新分支，`content_history` 留痕），或用 `memory_archive` 归档旧行后再让新事实自然入库——归档可恢复，且两行不再并存。
- **遗忘时按行操作并核对行内容**：`memory_forget` 之前先 `memory_get` 看这一行还装着什么；一行装着多个要分开处置的事实时，`memory_update` 先拆、再对单行遗忘。
- 工具描述已补一句行粒度警示（本 PR）：模型在「忘掉 X」的请求下，应当先意识到一行可能载着多个事实，并在回复里说清它抑制的是哪一行、连带了什么。

**Q2：更正所取代的旧事实，有没有持久失效关系，使隐藏新条目后旧值不会重新成为当前答案？**

**没有——这是插件层面的真实缺口，不是配置遗漏。** 失效关系今天只存在于两处：① `memory_register_document` 的同路径/同标题 supersede（#230，只覆盖 document 行）；② dream 冲突裁决的 loser 归档（阈值门控）。普通蒸馏行在 dream 第一次运行之前，旧行与新行之间**没有任何链接**。历史回溯与「当前答案」也因此无法区分：检索面对两行一视同仁，先后关系只体现在 `updated_at` 的排序权重里——模型答对（如 #532 对话 C）靠的是模型自己对比两行，不是机制保证。

**Q3：配置是否遗漏了该语义必需的原生设置？**

没有。`lightMode` / 阈值配置都在正常范围内；0.9.5 的已发变更（溯源读出口 #509、蒸馏围栏 #501、merge 逃生门 #521 等）都不触碰这条接缝。**#532 报告的现象在当前 main 上结构性地成立**，与 0.9.4 还是 0.9.5 无关。

## 3. 修复方向的取舍（需要维护者拍板，本 PR 不擅自实现）

| 方向 | 能修掉什么 | 代价 / 风险 |
|---|---|---|
| **A. 蒸馏提示词拆分粒度**（一事实一条） | 合流行被整条遗忘的连带伤 | 提示词级、行为面全变；行数增多（注入预算/检索排序全受影响）；LLM 遵从度不确定 |
| **B. 写侧更正失效关系**（蒸馏窗口内识别「同主题改值」→ 归档被取代行） | Q2 的缺口本体 | 「同主题」判据是 LLM 判断（dream 冲突裁决同款），放写入热路径要配阈值与误杀面测量——正是 dream 已经在做的事，重复建一套不如把 dream 的触发条件前移 |
| **C. dream 触发前移**（更正类写入直接计 dream 优先级 / 降低阈值） | 让现成的裁决机制更早介入 | dream 有成本（LLM 调用）；「更正类写入」的确定性判据同样不存在 |
| **D. 遗忘回执带同侪提示**（`memory_forget` 答复列出同 type+scope 的高相似活跃行） | 让模型在遗忘当下看到「别处还有旧值」 | 相似度判据要么依赖嵌入（可能未配）、要么是弱启发（误报面要测）；对已发生的遗忘只是事后提示 |

本 PR 只落地了零争议的一小块（工具描述的行粒度警示，见 §6）；A–D 的取舍涉及 LLM 判断进入哪条路径、误杀面怎么量，按 R2/R3 纪律停下等人拍板。**A–D 之外还有一件确定性的接缝已在 §5 修掉**：取代链存在时，遗忘继任者不再让旧值回潮。

## 4. 有界复测的最小合成轨迹（零 LLM）

不依赖任何模型行为，直接用存储/服务层复现「更正落新行 → 遗忘新行 → 旧值行幸存」：

```js
// 空库；严格 scope 不影响本现象，默认配置即可
const store = createStore(":memory:");
const service = createService({ store, mirror: null, config: {} });
// ① 原始陈述（模拟对话 A 的蒸馏产物：颜色 + 时间合流一行）
const r1 = service.saveWithDedupe({ type: "preference", title: "纸模工具的收纳与整理",
  content: "纸模工具放在雾蓝色收纳盒，每周三晚上八点整理一次", importance: 3 });
// ② 更正（模拟对话 B：标题由蒸馏器另起 → 三元组不命中 → 新行）
const r2 = service.saveWithDedupe({ type: "preference", title: "收纳盒颜色与整理时间的更正",
  content: "收纳盒换成浅橙色，整理时间改为每周六上午九点", importance: 3 });
// ③ 结构断言：两行同时活跃，二者之间没有任何失效链接
const activeCount = () => store.db.prepare(
  "SELECT COUNT(*) AS n FROM memories WHERE forgotten = 0 AND archived = 0"
).get().n;
assert.equal(activeCount(), 2);
// ④ 「忘掉颜色」= 按行遗忘新值行（模型在 R1/R2 里看到的颜色载体）
service.setForget(r2.memory.id, true);
// ⑤ 现象复现：新值行退出注入/检索面后，旧值行仍是唯一幸存载体
assert.equal(store.getById(r1.memory.id).forgotten, false, "旧行从未被任何机制波及");
assert.match(store.getById(r1.memory.id).content, /每周三晚上八点/, "旧值仍在召回面");
```

完整可跑版本见 `test/forget-corrections.test.js`（本 PR 附），其中 ④⑤ 两条断言就是 #532 现象的存储层等价物——机制修复（§3 的 B/C）落地时，这条测试的 ⑤ 应当翻转：更正行写入后，旧行要么被记上失效关系、要么退出活跃面；遗忘新行不应让旧值重新成为「当前答案」。

## 5. 取代链存在时的回潮缺口已修（2026-11-13）

§3 的 B 项（写侧自动识别「同主题改值」并落失效关系）需要 LLM 判断，仍按原文口径不开工；但链**已经存在**的那些库（#641 的 enforce 档会落 T3 取代链），§2 的 Q2 有一个确定性的反面：**继任者被 `memory_forget` 之后，被取代的旧行会重新成为当前答案**。

那是 #650 评审时为「继任者归档/遗忘/删除」统一加的守卫：`supersededIds()` 直接 JOIN 继任者并要求 `archived = 0 AND forgotten = 0`。理由（「数据在库里却永远不再出现是一种沉默的不可逆失效」）对**归档**成立——归档是整理面退场、可恢复、且常是合并落点；对**遗忘**不成立：`memory_forget` 的语义就是「我不要再记得这个内容」，继任者退场的理由是用户主动要求，不是「这个版本不再成立」。把被取代的旧值摆回注入面，等于让用户明确抛弃的答案趁虚回潮，正是 #532 主楼报的那句话。

现在两件事分开：

- **遗忘继任者**：旧行继续留在 `supersededIds()` 里 → 注入面不选它；但**显式搜索仍能读到**（`fuseRecall` 只降权 0.5，不摘除），所以不是沉默失效。
- **归档继任者**：按 #650 原语义恢复旧行可见性（回归锁在 `test/forget-supersede-chain.test.js`）。
- `memory_forget` 的回执现在报连带面：抑制一行时若它取代过 N 条更早的记忆，回执明写「它们保持隐藏、不应被当成当前值」——模型不必自己猜。

**仍然没修的**（如实记录，别读成闭环）：没有取代链的库（dream / sleep 未运行、或 `conflictLedgerMode` 关着）里，`memory_forget` 依旧按行抑制，§4 合成轨迹的 ⑤ 依旧成立。那一段属于 §3 的 B/C，需要 LLM 判断进入写路径，按 R2/R3 纪律等排期。

## 6. 本 PR 落地的零争议部分

- **`memory_forget` 工具描述补行粒度警示**（`src/tools.js`）：「抑制的是**一行**——多个事实合流在同一行里时，它们会一起退出可见面；请求只针对其中一个事实时，先看行内容、用 `memory_update` 拆分或在回复里说清连带了什么」。这是 #532 对话 5 里模型误用工具的直接对策：请求的语义粒度（一个事实）与工具的能力粒度（一行）之间的落差，模型无从得知，除非描述告诉它。
